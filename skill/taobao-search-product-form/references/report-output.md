# Comprehensive report output contract

Load this page at the `report` node. Its input is the run ledger and the completed modules' interpretation plus evidence artifacts, including any available cross-module evidence and opportunity cards. The report answers what product-side propositions merit further white-label research, why, and what evidence would change that assessment. It is a research report, not a binary entry authorization.

## Assembly main line

1. Resolve one coherent source run. Check source workbook identity, approved/verified module versions, natural-product population and advertising-row grain. The current visual prototype labels, prototype summary, comparison evidence, schema-2 opportunity cards and their source hashes form one linked version. Inspect the actual interpretation and evidence files. A changed visual classification requires new cross-module evidence, opportunity cards, visual interpretation and final report; unaffected modules from the same cleaned workbook may be reused after reconciliation. If a required module or source binding is absent, stop and reconcile before publishing.
2. Build the report data manifest from the current run's artifact paths. The `visual` module includes `summary`, `labels` (`product_style_labels.json`) and `prototypes` (`style_prototype_summary.json`); the `decision` module includes `evidence` and `cards`. Each opportunity-card document stores the comparison file's SHA-256 in `source_evidence_sha256`. A supplied visual interpretation Markdown starts with `<!-- source_prototype_summary_sha256: <64-character SHA-256> -->`; a supplied decision interpretation starts with `<!-- source_evidence_sha256: <64-character SHA-256> -->`. These binding comments are file metadata and are removed from rendered prose. When no visual interpretation has been written for the current prototypes, omit that role and label the report's data-derived explanation accordingly. The bundled `scripts/build_report_viewmodel.py --manifest MANIFEST --output NEW_VIEWMODEL.json` is the deterministic adapter for the current JSON/Markdown artifact family. The manifest uses semantic module keys, relative paths resolved from the manifest directory, a title, subject, and source identity; it is run data, never bundled private content.
3. Present a short executive reading path, then substantive independent chapters for input/cleaning, advertising, title roots, listing geography, price bands, visual form/style/task, candidate comparison, and opportunity judgment. Each completed analytical chapter contains its current-run written interpretation and evidence tables with explicit metric definitions and drill-down IDs. Use the source's numbered conclusions, bold leads, and labeled paragraphs as the semantic boundaries of numbered points. Each point states one complete judgment with its supporting figures, explanation, implication and relevant caveat together; its lead phrase is bold and its badge uses semantic color. Preserve every material finding, counterexample and limitation from the current interpretation; restructure headings and prose for reading without reducing the interpretation to a teaser. The visual chapter may synthesize its full-run label summary when no separately reviewed prose exists and must state that provenance. It includes structural-form and variant/configuration evidence tables plus a complete product-image gallery: one child menu per observed **whole-product style prototype**, with boundary and `未识图` menus when needed. Every natural product ID is covered; a listing may appear in several prototype menus when its image shows multiple actual styles, so menu counts cannot be added as unique products. Each card shows an HTTPS image, title, ID, shop, current price, displayed payment people, main form, variant/configuration, separate style, image-supported task, visual status and direct visible evidence. An original over 10 MB remains in the gallery and full numeric evidence with `未识图（图片不可用）` status and `too_large` reason; it has no inferred visual labels and does not enter visual candidate groups. Within each prototype show 50 items per page; sort the full prototype group before pagination by price, displayed payment, or the auditable research-priority score. Preserve the image-bound observations, prototype definitions, grouping reasons and uncertain cases in the run's audit; do not turn isolated visual features into report menus. Join the cleaned natural-position sheet's original `商品链接` to the gallery by product ID; verify URL scheme, marketplace host, embedded ID, source workbook hash and complete coverage. Each card has exactly two copy controls—ID and original link—and opening the image or title navigates to that link in a new tab. If links are unavailable or invalid in another input, expose the data gap instead of constructing a guessed product address.
4. The opportunity section is the synthesis, with one child menu per selected card. A card identifies the physical merchandise proposition, observations, supporting and adverse evidence, parent/comparable context, representative product and shop IDs, unknowns, and the next discriminating checks. Research order is explained; it is not an opaque total score or a go/no-go decision.
5. Provide a searchable evidence area including all natural products and candidate groups. Keep source text, IDs, titles, labels, price, displayed payment, shop, address and advertising linkage at their correct grains. The separate JSON artifacts remain the full machine-readable evidence. For a completed run-mode report, requested column filtering and sorting must be supported by the selected live contract; if not, use the reusable-template capability branch of `compact-commerce-ui`. In development mode an interim HTML may be delivered for user review with the missing controls named explicitly and the report stage kept `awaiting_review`.
6. Run `scripts/validate_report_viewmodel.py --manifest MANIFEST --viewmodel VIEWMODEL` before rendering to verify prototype-label/source binding, card/evidence binding, current interpretation versions, candidate/product/card coverage, and exact gallery membership per prototype. Reconcile every ready image to an observation and every unobserved product to a `too_large` manifest record; a missing readable-image observation fails QA. Render with the live `commerce-ui` template pack, not HTML written into this Skill. The report ViewModel is a separate artifact. Use the export's approved HTTPS links for the full gallery; selected representative thumbnails may remain embedded. Preserve the independent image-review contact sheet as an audit artifact.

The builder and validator match `visual.labels` to the comparison artifact's recorded prototype-label SHA-256, match `visual.prototypes` to each product's memberships, and match schema-2 opportunity cards to the exact comparison file SHA-256. These prototype memberships drive the gallery and allow justified repeat appearances across menus. Keep the source summary and three-axis labels as secondary evidence. The manifest is a run artifact, not a bundled category list.

## Evidence and presentation invariants

- Distinguish observed data, interpretation, counterevidence, unknowns and next research. Link each quantitative claim to the relevant row/group and product or shop ID; verify numbers against JSON, not merely against a prose file.
- Natural product ID is the product grain. Advertising occurrences, unique ad IDs and same-shop natural overlap are different measures. Title roots and visual candidate groups overlap and their totals are not additive. A blank use-task label does not establish absence of use demand.
- The export's `付款人数` has no stated time window; do not call it sales units, GMV, conversion or growth. Search-page price is not verified SKU transaction price. Title roots are seller claims. Listing address is not factory location. Image-supported task labels are not verified buyer demographics. A search snapshot does not establish trend, market share, ad spend, profit or white-label entry viability.
- The gallery's **research-priority score** is a transparent within-snapshot evidence-review order, never a predicted profit, white-label opportunity, conversion or entry score. Current default: `60 × min(1, ln(1+displayed payment people)/ln(1+payment P99)) + 25 × (product's price-band natural-product count / largest-band count) + 15 × (whole-product prototype assigned ? 1 : 0)`, rounded to one decimal. Derive P99 and band counts from the current unique natural-product sample, handle an all-zero payment sample safely, display those denominators and the formula, and keep the component assumptions visible. Higher price-band supply is evidence coverage, not proof of demand. Revisit the strategy with the user as product-level evidence improves; never silently treat the score as the research-card order.
- Present conclusions as short, labeled structured items, then numbered explanation points and evidence. Use semantic color and weight for pivotal claims and cautions. Let numbered source items and labeled source paragraphs define the point boundaries. Place the supporting explanation in the same point, with sufficient line spacing and selective emphasis; do not derive point boundaries from a fixed character count or punctuation. If a source paragraph contains several genuinely separate judgments, reorganize it by meaning and verify that each still has its relevant evidence and caveat. Preserve the complete approved interpretation content in readable chapter sections, including tables and case studies. Use only charts that make a comparison clearer than its table.
- Validate chapter and artifact coverage, source totals, card reference resolution, alignment between source judgments and numbered report points, UI navigation, evidence search/filter/sort as supported, image loading, desktop/mobile overflow and print readability. A generated file is `awaiting_review` until the user accepts it; a main run is not a clean-context regression.
