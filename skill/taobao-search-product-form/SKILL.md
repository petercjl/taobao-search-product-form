# Taobao search product opportunity research

## Purpose and boundaries

Input: a search-result workbook and the intended research object. Output: traceable intermediate evidence and a comprehensive HTML report answering what product forms merit further white-label research and why. This Skill does not infer market growth, advertising spend, profit, or actual buyer demographics from a single search snapshot.

The business flow is stable and complete; the methods used to classify products and judge opportunities are replaceable strategies. The stage list below defines **what must be handed forward**, not a fixed taxonomy, score, price-band scheme, or product recommendation. A strategy may originate from a user-confirmed method, a relevant Wiki source, or a tested proposal; record its source and version in the run ledger. Image-grounded form analysis is a required part of the current flow; its classification strategy can evolve.

This is a shareable Skill. The currently tested host is Codex on macOS. Read `capabilities.json` and the matching adapter when resolving execution capabilities. Do not claim other hosts tested without evidence. The workbook and public listing images are read-only inputs; no marketplace login, purchase, project update, publication, or paid action is implied.

When installed from the npm package, `taobao-search-form doctor --json` checks the local runtime and `taobao-search-form skill source --json` identifies the canonical Skill. Deterministic scripts can be run through `taobao-search-form script NAME ...`; this resolves package dependencies even when an Agent installation is a managed copy.

## Mode selection

- **Development mode (`development`)**: use when designing or changing this Skill with the user. Work on one stage or module at a time while building the complete flow. Preserve its real intermediate files. After producing a stage result, check it, record its artifacts and review state in `ledger.json`, and stop for the relevant design or result review before treating it as approved. Resume from approved artifacts instead of repeating earlier work. User confirmation is needed before marking a stage `approved`; an Agent's mechanical check alone is `awaiting_review`.
- **Run mode (`run`)**: use for an ordinary end-to-end request when the strategies and required capabilities are defined. Execute input, clean, all five current analysis modules, compare, decide, and report; perform each stage's automated QA, record results, and continue without routine user prompts. Stop only for a material missing choice, unavailable required capability, permission boundary, or failed quality gate that cannot be resolved safely. `verified` records automated QA; it is distinct from development-mode user approval.

Choose the mode from the request. An explicit request to co-design, tune, inspect, or approve one step uses development mode. A request to apply an established Skill to new data uses run mode. Do not silently treat unfinished design as a run-ready strategy.

## Shared business flow

The complete run follows all six stages in order. Development mode can inspect and approve one stage at a time; stage-level review is a design activity, not a shortened production run.

1. **Input.** Identify source workbook(s), search intent, target-product boundary, and available fields. Hand off the source identity and field inventory.
2. **Clean.** Split the source into separate natural-position and advertising-position tables. For natural-position rows, scan in source worksheet order and keep only the first row for each `商品ID`; later natural-position rows with that ID are excluded from the cleaned table. Retain all advertising-position rows as display records, including repeated IDs and IDs also present in natural positions. Keep the original source workbook unchanged, preserve its columns and surviving row order, and record source, retained and excluded row counts. Run `taobao-search-form script clean_search_export.mjs SOURCE.xlsx OUTPUT.xlsx` to produce the two-sheet local workbook. Treat blank IDs or unknown placement labels as input errors. Hand off this workbook and the quality counts; downstream modules use the relevant sheet and population.
3. **Classify and analyze.** Run all five current analysis modules: advertising placement, title terms, merchant geography, price bands, and image-grounded product form/style/audience. Each module consumes the cleaned data and records its own labels, statistics, evidence and limitations. Version each classification strategy separately from the stage. Additional modules may enrich the analysis without replacing these five.
4. **Compare.** Join outputs of all five modules at the natural product-ID grain, verify source identity and population coverage, and preserve module-specific grains such as ad appearances. Produce a reusable evidence dataset; state uncertain or incomparable observations.
5. **Decide.** Use the whole-product style prototypes as opportunity-card subjects. Structural form, product design style and image-supported use task explain and compare those merchandise propositions at the level the sample can sustain. For each selected prototype, produce an opportunity card with supporting evidence, counterevidence, key unknowns, representative products and shops, and the next discriminating checks. Research order may be proposed with reasons; the user makes the entry decision. Research priority is not authorization to source or stock goods.
6. **Report.** Assemble a comprehensive, conclusion-first HTML report from every completed module's reviewed interpretation **and** its traceable evidence artifact, then the cross-module comparison and opportunity cards. Each module keeps a substantive chapter with numbered, scannable *complete judgments*: a source conclusion, its supporting figures, interpretation and caveat stay together as one point. Use semantic emphasis while preserving its evidence. The visual chapter contains the full product-image gallery, grouped into whole-product style-prototype child menus; a listing may appear in several menus when its image contains multiple real styles. Keep structural form, variant/configuration, style and task visible on each card, 50 items per page and full-group sorting by price, displayed payment or an explicitly defined research-priority score. Preserve each source product link so the card offers separate copy-ID and copy-link controls and opens the product from its image or title in a new tab. Load `references/report-output.md` only at this node for the chapter, evidence and QA contract. Resolve the exact `compact-commerce-ui` Skill from the current host, read its current complete `SKILL.md` and live CLI contract, create the ViewModel, render through `commerce-ui`, and validate the artifact. Return to this node after the nested Skill completes. In development mode deliver a new report version as `awaiting_review`; in run mode finish after automated QA without routine user interaction.

The five analysis modules and the final HTML report are required deliverables of a run. Development-mode reviews may stop at the current stage and retain its intermediate result for the next design step.

## Run ledger

Keep execution state outside the Skill in the chosen run directory. Use `scripts/workflow_ledger.py init --run-dir RUN_DIR --mode development|run --input WORKBOOK` once. `ledger.json` tracks each stage's `design_state`, `status`, strategy reference, evidence/artifact paths, review note and event history. Use `record` after each material transition and `show` when resuming. The CLI refuses to initialize over an existing ledger, verifies declared artifact paths, and backs up the previous ledger before updating it. See `references/workflow-ledger.md` for the minimal command contract and state meanings.

In development mode, an executed stage normally ends at `awaiting_review`. Record `approved` only after the user's confirmation, with the reviewer and evidence. Record completed parent stages (`classify`) and downstream stages (`compare`, `decide`) as soon as their artifacts exist; a report's approval does not silently approve separate stage results. A changed visual-classification strategy or input invalidates the compare, decide and report artifacts: mark those stages `not_started` with the reason, regenerate their evidence and interpretations, and record their new source hashes before advancing. Previously approved unaffected modules from the same cleaned workbook may be reused after their source hashes and populations reconcile. In run mode, `verified` means the applicable automatic checks passed; update the ledger after every material transition, including completed long-running visual batches. Never infer success from a file name alone: inspect the file and record what was checked.

The ledger is a pointer to intermediate results, not their replacement. Preserve source identity, exact output paths and enough stage context to resume another day. Do not put private run paths or user data into this distributable Skill.

## Current method routes and execution resources

Load knowledge only when the current knowledge-dependent node needs it; later-node pages remain deferred. At the first visual-form judgment node, read `references/SCHEMA.md`, `references/index.md`, recent `references/log.md`, then `references/queries/identify-product-forms.md` and only its routed topics. Complete this orientation before expensive image inspection. At a white-label judgment node using the current evidence method, load `references/queries/evaluate-white-label-forms.md` and its routed topics. Return to the selected business-flow node after each route. Do not load the whole knowledge layer at startup; `source-manifest.md` is maintenance provenance.

When selecting **visual product forms** (`classify/visual-form`), follow the routed visual method. Use `scripts/visual_form_pipeline.py plan --manifest IMAGE_MANIFEST --output-dir NEW_DIR [--batch-size 10]` to produce disjoint, image-hash-bound review batches and legible contact sheets. The planner consumes a prepared image manifest and plans natural-position products only; reconcile its product IDs and first natural records with the approved cleaned workbook before analysis. An original image exceeding 10 MB is marked `too_large`: retain that product in the natural population and report, mark its visual status `not_observed`, exclude it from visual candidate aggregation, and continue with the readable images. Record the omitted ID, count and reason; every `ready` image still requires a semantic observation, and other fetch failures require diagnosis or retry before completion. The image fingerprint is solely a scheduling aid. The default execution path is **serial, resumable semantic review**: use the host's tested local-image inspection capability to inspect each contact sheet (zoom an unclear source image), write one three-axis observation per ready product in that batch, and commit it with `scripts/visual_observation_batches.py commit --plan PLAN.json --batch-dir BATCH_DIR --batch-id B001 --draft DRAFT.json`. Call `status` with the same plan and batch directory to locate the next uncommitted batch, and continue until none remain; record progress in the run ledger after material batch groups. A large batch count or unverified parallelism is not by itself a capability failure. If the active turn or context ends, preserve the committed batches and resume from `status`; report incomplete only when execution actually cannot continue, identifying the last committed batch. The parallel-observe capability is optional acceleration only when its real worker count and outputs are verifiable. In one image-semantic pass per ready product, record structural form, product design style and target use-task/audience evidence; preserve this original image observation separately from later inference. After all batches are committed, merge them with `scripts/visual_observation_batches.py merge` and keep the three-axis compiler output as evidence, not as the final product-style taxonomy.

The final visual classification unit is a **whole, sourceable product-style prototype**: a recognizable physical product scheme that can be compared as a merchandise option. From a varied image sample, discover run-specific prototypes with complete product definitions, representative images, distinguishing configuration/design and inclusion boundaries. Compare every ready product with the prototypes; add a prototype when a materially different sellable product scheme appears, then revisit earlier near neighbors. A product image containing several distinct real products may belong to several prototypes; ordinary color/size variants remain within one prototype. Keep isolated body/handle/lid/spout/surface features as evidence or variant fields, not as substitute style classes. Use image evidence for visible structure and design; material claims, buyer identity and use suitability remain uncertain until separately corroborated. A saved image-hash-bound observation may be reused for re-aggregation; reopen representative or ambiguous originals when its description cannot resolve a style boundary. Record one decision per ready product, the versioned prototype registry, reasons for close merge/split decisions, uncertain/boundary items and example images. Validate with `scripts/compile_style_prototypes.py --plan PLAN.json --observations OBSERVATIONS.json --decisions DECISIONS.json --output-dir NEW_DIR`; it checks coverage, source hashes, prototype references and multi-style membership, then emits per-product labels, group summary and audit. Inspect each group's representative and exceptional images, plus similar groups across the registry. Use these prototype groups for downstream comparisons and report navigation; preserve earlier structural/style/task labels as secondary evidence. Report observed sample size against the full natural population; pilot results remain pilot-only. Register the plan, batch checkpoints, merged observations, prototype decisions, compiled labels/summary/audit and interpretation under `classify/visual-form`; development mode stops at `awaiting_review`.

When the selected module is **who appears in advertising positions** (`classify/placement`), first load `references/SCHEMA.md`, `references/index.md`, recent `references/log.md`, and `references/queries/identify-advertisers.md` with its routed topic. Return to stage 3 and run `scripts/analyze_advertisers.py --input CLEANED.xlsx --output NEW.json`; optionally pass run-specific `--price-bands` chosen after inspecting the price distribution. The input is the clean-stage two-sheet workbook. The JSON holds separate advertising-appearance, unique-product and operating-shop grains; it preserves original display labels and resolves a known platform label to the actual shop only with same-ID shop-name and seller-name corroboration; advertiser-shop natural-position product layout; natural-row `付款人数` for matching products and shops; comparable price-band distributions; definitions and reconciliation checks. Use only natural-row `付款人数` as the observed transaction-traction field. Then write a substantive UTF-8 Markdown interpretation for the later HTML report. Select representative, contrasting advertiser shops by observed advertising presence, advertised-versus-unadvertised assortment, natural-position payment evidence, and price positioning. For each selected shop, identify the actual advertised listings and key non-advertised natural listings, explain the observed merchandise/placement configuration, distinguish plausible intent from measured fact, and derive a concrete implication for the next white-label product-form investigation. A cross-shop synthesis must distinguish recurring patterns and prioritize what to inspect next; aggregate statistics provide context rather than replacing the cases. Follow the case-selection and evidence contract in the routed advertiser method. Every named claim must trace to JSON records, and any missing natural record stays unknown rather than zero. The JSON is the detail artifact; the Markdown is the human-readable conclusion artifact. Check every stated figure against the JSON and register both paths under `classify/placement`. Development mode may stop here for user review before the next module is designed. Advertising rows are observed placements, not spend or actual impressions; shop-type labels do not verify brand ownership; natural `付款人数` has an unspecified time window and is not GMV, unit sales or storewide sales.

When the selected module is **natural-position title roots** (`classify/title`), first load `references/SCHEMA.md`, `references/index.md`, recent `references/log.md`, and `references/queries/identify-title-roots.md` with its routed topic. Return to stage 3 and run `scripts/analyze_title_roots.py --input CLEANED.xlsx --output-dir NEW_DIR`, optionally adding `--project-lexicon REVIEWED.json`. Discover a Python with pandas, XLSX reading support and a package exposing `jieba`: probe `TAOBAO_SEARCH_PYTHON` when configured, an existing user-managed `$HOME/.local/share/taobao-search-product-form/.venv/bin/python` on Unix-like systems, then working interpreters on `PATH`; verify the actual imports before running. The home-relative venv is a discovery convention, not a required platform path. If none qualifies, install the dependencies in a supported stable user environment or report the exact gap. The bundled `references/title-lexicon.json` holds general protected phrases and aliases; each run writes its merged lexicon snapshot and new-word candidates without changing the bundled or project dictionary. The script creates product, product–root, root, shop and cross-facet-pair evidence from the cleaned `自然位` sheet only. Review the JSON quality counts and representative segmentation cases, then write a separate evidence-backed human conclusion. Interpret title words as seller claims/SEO language; the source search phrase is the buyer query, and actual product form awaits image review. Use distinct product IDs when aggregating; root-level payment sums overlap and cannot be added across roots. Register the four JSON files and conclusion under `classify/title` in the ledger. Development mode may stop here for user review.

When the selected module is **listing location and merchant geography** (`classify/geography`), load `references/SCHEMA.md`, `references/index.md`, recent `references/log.md`, and `references/queries/identify-geography.md` with its routed topic. Return to stage 3 and run `scripts/analyze_geography.py --input CLEANED.xlsx --output-dir NEW_DIR`, adding `--title-roots PRODUCT_ROOTS.json` when an approved title-root artifact from the same cleaned workbook is available. The two JSON outputs preserve unique natural products, exact shops, shop–address pairs, region statistics, optional title-root–region cells, and separate advertising appearances and unique products. Check workbook-hash and product-title joins, multi-address shops, missing locations and independent count reconciliation. Write an evidence-backed Markdown conclusion and register all three artifacts under `classify/geography`. The exported `地址` is an observed listing label; it does not verify dispatch warehouse or factory location. Do not turn regional listing concentration into a production-cluster claim. Development mode stops here for user review.

When the selected module is **sample-derived price bands** (`classify/price`), load `references/SCHEMA.md`, `references/index.md`, recent `references/log.md`, and `references/queries/identify-price-bands.md` with its routed topic. Return to stage 3 and run `scripts/analyze_price_bands.py --input CLEANED.xlsx --output-dir NEW_DIR`. The module uses every cleaned natural-position product; product eligibility belongs to the upstream clean stage when needed, not this price module. Advertising appearances are mapped against the natural-derived boundaries but do not fit them. Jenks natural breaks on log current price produces candidate boundaries; the declared complexity penalty selects a band count from sample fit, and bootstrap resampling checks boundary stability. Read `price_band_detail.json` and `price_band_summary.json`, then write a separate evidence-backed Markdown interpretation for the later HTML report. Explain the actual fitted boundaries, band populations, merchant spread, observed payment and advertising context, selection criterion, sensitivity, and limitations. Boundaries are run-specific and must never be reused as a default for another search. Displayed current price is not a verified transaction/SKU price; price clustering describes visible supply, not proven buyer price psychology or white-label opportunity. Reconcile all natural IDs and advertising appearance counts, register the three artifacts under `classify/price`, and stop for development-mode review.

When the selected node is **cross-module comparison** (`compare`), use `scripts/assemble_opportunity_evidence.py --visual-labels PRODUCT_LABELS.json --prototype-labels PRODUCT_STYLE_LABELS.json --price-detail PRICE_DETAIL.json --title-roots PRODUCT_ROOTS.json --geography-detail GEOGRAPHY_DETAIL.json --advertiser-detail ADVERTISER_DETAIL.json --output NEW.json` using the five completed module artifacts and compiled whole-product style labels. It verifies the common cleaned-workbook hash for numeric modules, reconciles natural product IDs, key fields and visual image hashes, accepts a visual subset only when its IDs belong to that natural population, and keeps advertising appearances separate. Its output contains one record per natural product and candidate groups at product-style prototype and secondary form/style/task grains. These groups overlap by design: never add their totals together. `uncertain` visual products remain in the product table but outside tagged candidate aggregates; an unknown task is not evidence of no task demand. If a required module artifact is missing, stop the full run and report the missing evidence instead of producing a narrower opportunity judgment. Inspect the output's reconciliation and source hashes, then record it under `compare`. Return to stage 5.

When the selected node is **white-label opportunity judgment** (`decide`), load `references/SCHEMA.md`, `references/index.md`, recent `references/log.md`, and `references/queries/evaluate-white-label-forms.md` with its routed topic before interpreting candidate groups. Select whole-product style prototype candidates as the card subjects; use secondary form/style/task groups as comparisons and evidence cuts. Produce a versioned schema-2 `opportunity_cards.json` plus a readable Markdown rendering from the current comparison artifact. The card document records `source_evidence_sha256`, the exact SHA-256 of that artifact; each `candidate_id` resolves to its `product_style` axis. Each card identifies the concrete product-side proposition, observed demand and price signals, merchant-line and advertising configuration, supporting and adverse evidence with product IDs or group metrics, unknowns, and the next question whose answer would change the assessment. Keep the semantic judgment out of the aggregation script. The default card is an evidence display and research-order suggestion, not a binary go/no-go verdict or an opaque total score. Run `scripts/validate_opportunity_cards.py --cards CARDS.json --evidence EVIDENCE.json` to check source binding, card structure and reference resolution; separately audit the meaning and arithmetic of every stated number. Preserve conflicts, and register both outputs under `decide` as `awaiting_review` in development mode. Return to stage 6 to produce the required HTML report.

`scripts/prepare.py`, `scripts/compile_visual_review.py`, and `scripts/analyze.py` remain available for the current workbook and image-form path. Their use is recorded in the ledger, including the actual scope. The clean-stage two-sheet workbook is the authoritative handoff for later modules; where an older script reads raw rows directly, reconcile its natural-position population and first-record fields against the clean workbook before using its results. Derive visual form from inspected images rather than title or platform category. An ad-only product may inform advertiser analysis but not inflate natural-form counts. If images or labels cover only a pilot, label both denominator and conclusions as pilot-only. Displayed `付款人数` has an unspecified window; do not turn it into GMV or a growth trend.

## Completion and evolution

Before advancing a stage, check its actual artifact, source coverage and uncertainty, then record its state. Before handing off a full report, reconcile displayed counts to the intermediate results and validate images, links, navigation and readable layout through available permitted capabilities. If a required capability is unavailable, report the precise gap instead of silently weakening the output.

Development decisions refine the appropriate layer: stable order and hard boundaries here; evolving classification or decision methods in routed references; fixed transformations in scripts; evaluation cases outside the runtime Skill. Change only the affected layer, verify the written files, and test the changed path. A clean-context regression is separate and only runs when the user explicitly requests it after accepting a standard artifact.
