# Image-grounded form judgment

The upstream clean stage defines the product population. This module describes what is visible in its images; if a main object is ambiguous or appears outside the intended product boundary, flag it for that upstream decision rather than silently deleting its record. The image may disagree with a title or platform category.

## One semantic read, three selection dimensions

Before the first image call, create disjoint batches and record each readable product ID, image path/hash and batch ID. An original exceeding 10 MB is a `too_large` image-manifest item, retained in the natural-product evidence as `not_observed` and excluded from semantic batches and visual candidate groups; its title cannot substitute for an image observation. Record its ID and omission reason, then continue with the readable images. A visual worker receives the same questions and any provisional registry snapshot, but no closed list of allowable labels. For each ready product, capture one raw observation with `product_id`, `image_sha256`, `batch_id`, `status`, `visible_evidence`, and three independent dimensions:

1. `form`: one candidate structural class, evidence and visible traits such as outline, depth, divisions, size and handle/lid relationship. Assign `uncertain` if the structure cannot be resolved. Color alone never splits a structural class.
2. `style`: optional candidate product-design style, at least two concrete product-side cues, and a possible physical design delta. Keep main-image background, copy, lighting and graphic treatment in a separate `image_presentation` note. A style name derived only from one color is too weak and remains a cue rather than an accepted style class. Leave style unclassified when the product is visually generic or obscured.
3. `audience`: optional candidate group defined by a use task, visible task cues, an explicit evidence tier (`image_only`, `combined`, or `insufficient`), and a plausible product-side adaptation. A depicted egg is a task cue, not proof of the buyer's demographics or actual purchase behavior. A candidate audience requires a task that could change the product's size, structure, handling, set configuration or design. If there is no such evidence, leave it unclassified. Any later title/price corroboration is recorded as a separate join, not retroactively presented as image evidence.

The three dimensions are parallel selection paths. A style-led or audience-led physical product difference can constitute a new candidate merchandise proposition even when its base structural form matches another product. Distinguish candidate proposition from demonstrated opportunity: a single search snapshot cannot prove demand, profit or actual buyer identity.

Review contact sheets serially in small batches by default. Save each completed batch as an immutable, plan-bound checkpoint before moving on, and use the batch status command to resume after a context boundary. A contact sheet may contain several images, but every product must remain independently keyed; the batch draft uses `{"schema_version":2,"observations":[{"product_id":"…","status":"tagged|uncertain","visible_evidence":"…","form":{"candidate":"…"},"style":{"candidate":null},"audience":{"candidate":null}}]}` with the evidence fields above when style or audience is proposed. The checkpoint command binds each row to its planned image hash and rejects missing or extra IDs. Zooming one unclear original is an explicit QA exception to the single-pass aspiration; log it. Use bounded concurrent semantic workers only when the host actually supports parallel image understanding and their outputs can be reconciled; each worker owns disjoint product IDs. Unverified parallelism never blocks the serial path, and image-download concurrency does not count as semantic concurrency.

## Product-style prototype convergence after the image reads

The three raw observation dimensions are useful evidence, but the final classification answers a different question: **what distinguishable merchandise styles can the seller actually choose, compare, source or develop?** A prototype is a coherent real-product scheme described through several jointly visible cues: base object, construction and handling, key functional configuration, and (when material to selection) an integrated product-design language. A single feature count—body silhouette, lid, spout, color, surface texture or photographed food—is not itself a complete style. A prototype name should let a merchant picture the actual good, such as “锤纹雪平锅” or “蒸煮一体小锅”, without requiring the source title to complete its meaning.

1. Start with a varied image sample rather than a fixed category dictionary. Sketch candidate prototypes with a physical definition, sourceable selection difference, representative product IDs, inclusion and confusion boundaries. Use the original images and saved visible observations. The prototype registry is run-specific and can grow as new physical schemes appear.
2. Compare each later product with representative and boundary images. Assign it to an existing prototype when differences are ordinary size, color or selectable configuration variants. Create a new prototype when the whole structure, function set or distinctive finished-product design demands a different comparison or supplier-development task. Revisit earlier near neighbors after a new prototype is introduced. A real rare prototype remains visible with its small count.
3. A main image containing multiple recognizable goods can associate its listing with multiple prototypes; a hybrid good can likewise support more than one selection-relevant proposition. Preserve the product ID once in the population and record every justified membership. Keep ordinary variant details and single visual cues in separate fields so groups stay interpretable. Image presentation, graphic copy, inferred material, buyer demographic and unsupported use claims cannot create a prototype.
4. Keep out-of-object accessories, image-only promotional compositions, unresolved objects and unreadable images in explicit boundary/uncertain states. Do not silently delete their product IDs. Class membership is image-grounded; title, price, payment or shop data cannot decide the visual class.
5. Review group cohesion with representative, edge and low-confidence images, then compare near-neighbor groups for missed same-style merges. A group is useful when its members look like a coherent sellable product line and its distinction from another group would change the next selection investigation. Record merge/split reasons and remaining uncertainty; a smaller class count alone is not proof of quality.

Keep the raw observations immutable. A classification pass writes a versioned registry plus one decision for every planned ready product: `product_id`, `image_sha256`, `style_ids` (one or more), `variant_or_features`, `reason`, `confidence`, and optional `boundary_reason`. The registry records `style_id`, name, physical definition, selection difference, inclusion/boundary rule and representative IDs. The deterministic `compile_style_prototypes.py` validates this decision file against the original plan and observations, then outputs product-level labels, prototype summary and an audit. Re-aggregation may reuse the saved image-hash-bound observations; reopen an original when its description does not settle a consequential boundary. New product images still require their own semantic observation.

Use prototype groups in downstream joins and report navigation. Preserve structural form, design style and use-task observations as secondary evidence and filters. Reconcile `ready = observed = style-decided` and `too_large = not_observed` before full-run reporting; other unavailable-image reasons require diagnosis or retry. Count distinct product IDs for population and demand comparisons because prototype memberships can overlap. Join price, natural payment counts, shops and advertising only after the visual classes are finalized. This stage describes visible supply options, not buyer demand or entry feasibility.
